# probe: repo-guard（仓库规范）

**required: true** ｜ **requires: rules** ｜ `read_only: true`

## 只检查，不改代码

本探针在 review 过程中**不修任何东西**。发现的问题一律产出 finding 交下游处理。
理由：review 阶段顺手改代码会让「被审的代码」和「审完的代码」不是同一份，
审查区间当场失效，而且改动没有经过测试的红绿循环。

## 步骤

规则包位置，按优先级取第一个存在的：

1. `$CODE_REVIEW_RULES_DIR`
2. `<项目根>/.code-review/rules/`
3. `references/rules/`（skill 内置）

先读所选规则包的 `index.md`，了解规则主题。项目自带规则包会**整体替代**内置规则包，不合并。

### 3.1 规则扫描与候选复核

审查范围和代码版本以主流程 `SKILL.md` 的“确定审查范围”为准。

1. **选择文件**：从变更清单中选择 `.java` / `.ts` / `.tsx` / `.vue`，
   包含新增文件，排除已删除文件；无适用文件时转入 3.2。
2. **运行扫描**：将文件路径逐个作为独立参数传给
   `bash "$CODE_REVIEW_SKILL_DIR/scripts/rule-grep"`。
   脚本扫描文件全文，命中位置可能包含旧代码。
3. **AI 复核**：结合对应规则、代码上下文和本轮差异，确认是否确实违规。
   仅将本次改动引入或触发的问题纳入 finding；无关旧问题单独记录，不计入本轮计数。

无法用模式判断的相关规则，转入 3.2。
磁盘文件与审查目标版本不一致时，读取目标版本源码，按 3.2 进行 AI 语义检查。

扫描只提供候选；命中不等于违规，未命中不等于合规。

### 3.2 按需加载与 AI 语义检查

AI 语义检查指由 AI 读取规则正文、diff 及相关代码上下文，判断规则是否适用、代码是否确实违规。

根据索引、项目语言、改动主题及扫描命中项，按需加载对应规则文件。
散文类、不可机判但与改动相关的规则也须加载，不能只检查扫描命中项。
缺省检查主题包括：

- SQL 注入
- XSS
- 鉴权与权限隔离
- 敏感数据处理
- 硬编码凭证
- 幂等性

具体要求以本轮选中的规则文件为准。

对已选规则与本次改动逐条比对，报告注明实际加载的规则文件和检查范围。
只对 CRITICAL / HIGH 级别规则产出 finding。
发现规范违规时记录**适用的规则 ID、文件、行号、违规描述**。
行为正确性问题按 3.3 检查并提供证据。

### 3.3 行为正确性检查

对关键行为，先按顺序取证，再推演和定级：

1. 定位实际调用的完整方法签名，读取对应接口声明及该方法自身的契约；不能用同名重载或相似接口代替。
2. 涉及模型或缓存读取时，沿对象获取、创建和包装路径，读取实际返回实现及相关覆写方法；不能仅按接口字段或默认实现推断返回值。
3. 结合上述源码推演触发条件与结果，再按输出契约定级。关键材料未核实时，注明检查限制，不得宣称该路径正确或检查完整。

对本次改动影响的主要路径，结合入口、调用方和上下文检查：

- 条件分支是否符合预期，是否存在判断反向或遗漏分支。
- 状态转换是否允许，副作用是否在正确条件下执行。
- 空值、空集合和数值边界是否处理正确。
- 异常或部分失败后，状态与资源是否正确处理。
- 重复调用、重试、并发是否破坏业务约束。

针对主要行为变更选择反例，检查等价写法、特殊字符等相关边界是否仍符合预期。
报告简记反例与结论；未运行时标明“静态推演”，不得称为已复现。

行为问题的 `evidence` 必须说明：
**触发条件 → 相关代码路径 → 预期行为及依据 → 实际行为与后果**。

预期依据可来自接口契约、设计、已有测试或明确的代码不变量，不得自行编造业务规则。
证据不足时记录为未验证项，不能仅凭“看起来危险”认定存在问题。
每条 finding 仍须按 `references/output-schema.md` 记录稳定 ID，不要求已有规则 ID。

## 判定与上报

定级、执行状态及上报方式见 `references/output-schema.md`；`name` / `required` 取自注册表。
规则包目录不存在或一个规则文件都读不到时，记为 `error`。

报告注明实际检查范围、结论及未验证项；具体问题逐条举证。

## 反模式

- ❌ 只检查扫描命中项，遗漏与改动相关、需 AI 语义检查的规则
- ❌ 顺手改代码「反正就一行」
